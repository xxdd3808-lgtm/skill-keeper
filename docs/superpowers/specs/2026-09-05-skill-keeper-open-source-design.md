# skill-keeper 精简开源泛化设计

**状态：** 用户已确认精简方向

**日期：** 2026-09-05

**对应计划：** [skill-keeper-open-source-upgrade.md](../plans/2026-09-05-skill-keeper-open-source-upgrade.md)

## 1. 产品目标

skill-keeper 要解决的是一台电脑安装多个 Agent 客户端后出现的三个问题：

1. Skill 分散在不同目录，不知道各客户端实际有哪些；
2. 同一 Skill 有多份副本、不同版本、链接或插件缓存，容易重复加载和漂移；
3. 删除、更新和恢复缺少统一备份、验证和回滚。

开源泛化只需保证：三个操作系统可以运行；已知客户端保持现有精确能力；未知客户端能把本机 Skill 根目录交给 skill-keeper；所有真实变更继续安全可恢复。

## 2. 最关键的简化

大模型不需要列出每一个 Skill，也不需要向项目提交回执。它只提供当前客户端的本地 Skill 根目录：

```json
{
  "schema_version": 1,
  "client": "example-agent",
  "observed_by": "model",
  "complete": false,
  "roots": [
    {
      "path": "~/.example-agent/skills",
      "scope": "user",
      "load_state": "reported"
    }
  ]
}
```

这叫“位置声明”，不是资产清单。skill-keeper 收到后在用户电脑上自行扫描目录、读取 SKILL.md、计算指纹和判断重复。声明不包含 Skill 名称、正文、来源台账或账号，也不上传。

大模型由此成为“运行时客户端适配器”：

1. 识别当前系统和客户端；
2. 根据当前上下文、客户端文档或可用工具找到 Skill 根目录；
3. 通过 CLI 参数或标准输入把位置交给 skill-keeper；
4. skill-keeper 用确定性程序验证路径和目录内容。

新客户端通常无需进入项目代码，也无需等待项目更新。现有 Python 适配器继续服务当前私人环境，提供更准确的加载顺序、插件缓存和 builtin 规则。

## 3. 最小架构

```text
现有精确适配器 ──────┐
用户本地配置 ─────────┼──► Location 列表 ─► 现有扫描/指纹/体检/报告
模型临时位置声明 ─────┘                          │
                                                ▼
                                  现有计划/备份/事务/回滚/审计
```

只增加三个薄接口：

- **统一 CLI：** 让所有平台和 Agent 使用同一组命令；
- **位置输入：** `--root CLIENT=PATH` 或 `--locations-json FILE|-`；
- **平台工具：** 跨平台绝对路径判断和文件锁，写操作前在真实目标旁做最小预检。

不增加客户端注册中心、社区回执、遥测、远端服务、客户端 profile 市场或新的身份体系。

## 4. 证据规则

沿用项目现有的 discovered / eligible / confirmed / unknown 思路：

- 本机扫描确认“文件存在”；
- 现有适配器和 load rules 可以判断“按规则可加载”；
- 模型声明只能记为“客户端报告该位置可见”；
- 观察不完整时保持 unknown，不能推导“没有其他 Skill”；
- 多种证据冲突时保留冲突，不能让模型覆盖本机事实。

模型提交的根目录默认只读。它不能提供 `mutable=true`、instance ID、tree hash、删除建议或命令。只有用户本地 `client-locations.json` 明确登记为 mutable 的根，以及现有适配器认定可写的根，才能产生变更计划。

## 5. 隐私设计

- 默认不联网、不上传、不遥测；
- 位置声明通过命令参数、标准输入或本地临时文件进入；
- 原始声明不单独持久化，inventory 只保留现有报告所需的 home-relative 显示路径和证据类型；
- 不记录 Skill 正文、完整 HOME、客户端账号、提示词、token、key、cookie 或 env；
- 不提供社区兼容性报告上传功能；
- GitHub 证据查询仍是现有可选功能，与位置声明分开。

## 6. 跨平台只处理必要差异

跨平台运行不需要完整“能力检测平台”。只处理当前代码中会实际阻塞的边界：

1. `fcntl` 改成 POSIX/Windows 两个标准库锁后端，外部接口不变；
2. 路径判断使用当前系统的原生绝对路径规则，Windows 支持 drive 和 UNC；
3. 新安装统一把状态放在 `~/.skill-keeper/`，避免维护三套系统目录；显式环境变量和现有仓库 data/backups 继续优先；
4. apply 时在目标同目录创建工具自有临时对象，实际验证可写、同卷移动和回滚；失败立即清理并拒绝；
5. 遇到 Windows 无权创建的 symlink、无法还原的权限或被占用文件时，针对该计划拒绝，不影响扫描和报告。

这种“执行前在真实目标上验证”比预先维护一张操作系统能力表更准确，也更少代码。现有事务和备份逻辑继续负责失败回滚。

归档内部路径仍使用 POSIX `/` 并严格拒绝反斜杠、绝对路径和 `..`。本机 Windows 路径另行判断，不能借跨平台之名放宽归档安全边界。

## 7. 保留私人版的方法

现有适配器、load rules 和以下个人配置全部保留：

- groups.json；
- self-built.txt；
- known-sources.json；
- ignore.json；
- workspace-locations.txt；
- client-locations.json；
- value-reviews.json；
- 现有 backups、ChangePlan 和审计记录。

证据优先级保持：用户本地确认 > 本机文件事实 > 已验证适配器 > 模型位置声明。升级不改变现有 instance ID、logical ID、tree hash、备份格式和审查绑定。

## 8. 本轮明确不做

- 不收集或上传用户回执；
- 不建立遥测或服务端；
- 不维护“所有客户端名单”；
- 不为新客户端开发专用适配器或 profile；
- 不增加跨机器 portable hash；重复判断只针对当前电脑；
- 不做完整平台 capability 模型；改为 apply 前目标预检；
- 不重做网页报告、主题或筛选器；
- 不扩展运行态迁移系统；沿用已有迁移预演；
- 不增加数据库、模型 API、守护进程、云端 Skill 同步或客户端商店；
- 不在发布前人工测试所有操作系统和客户端；
- 不发布客户端支持等级排行榜；
- 不承诺管理没有本机文件或文件工具的纯云端 Skill。

## 9. 完成后的用户能力

已知客户端用户继续获得完整盘点、加载重复检测、来源审查、价值审查、更新检查、备份、删除、更新、恢复和审计。

未知客户端用户让模型找出本机 Skill 根目录后，即可：

- 盘点该目录的 Skill；
- 与其他客户端的实例一起识别重复、版本漂移、损坏 frontmatter、悬空链接和嵌套 Skill；
- 在报告中区分本机发现、规则推断和模型报告；
- 把确认过的根写进本地 client-locations.json，长期复用；
- 对明确标记为 mutable 且通过现有安全策略的本机实例执行计划化变更。

## 10. 验收方式

AI 执行者按 Task 0–5 串行完成。阶段测试通过后自动继续，不需要用户逐项验收。GitHub Actions 在 Windows、macOS、Linux 上自动验证安装、扫描、报告、锁、路径和事务。

项目不再等待人工客户端烟雾测试。无法从自动证据确认的客户端行为在报告中保持“客户端自报”或 unknown。push、tag 和 GitHub Release 仍需用户给出发布授权，但可以由 AI 代为执行。
