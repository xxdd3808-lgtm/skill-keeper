# skill-keeper 演化复盘与优化依据

审视日期：2026-09-05。代码基线：`f044e1732e1fa1f620a2bed641e1542fb553b047`。本文件是审视结果和后续计划的依据，不代表优化已经实现。

## 1. 判断

这个项目值得继续做，下一轮应优先兑现现有承诺。

它最有价值的部分，是把散落在不同 AI 客户端的 Skill 变成用户能够理解、比较和安全处置的本地资产。当前瓶颈不是缺少更多客户端、更多分数或更漂亮的主题，而是几个关键承诺还没有贯通：**看见的是不是完整事实，建议是否仍然有效，确认的是否就是执行的对象，失败后能否恢复原状。**

建议下一轮采用“先修复可信性，再收拢共同规则，再补齐操作闭环，最后优化计算”的顺序。保留纯 Python 标准库、本地文件、确定性证据与 AI 语义判断分工；不做整体重写。

## 4. 从第一性原理重新定义目标

用户要的结果是：维护较低成本的一套有效 Skill，且不用担心错误建议或误操作破坏自己的工作流。

因此应优化的是：错误事实/错误变更造成的损失、用户做决定的成本、系统长期维护成本。Skill 总数下降、GitHub 星数上升、报告卡片增多、测试数量变大，都不是目的本身。

必须守住六个关系：

1. **发现 ≠ 加载 ≠ 使用。** 文件存在只能证明发现；加载取决于客户端、版本、启用状态与工作区；实际使用必须有额外证据，不能从安装推断。
2. **内容 ≠ 身份。** 树哈希适合表示某份内容版本；安装路径/来源与历史记录才能连接前后版本。内容变更应让结论失效，并保留历史。
3. **受保护 ≠ 安全。** 受保护意味着由谁管理、能否由本工具变更，不意味着跳过所有内容风险提示。
4. **校验过的备份 ≠ 可恢复的备份。** 必须验证完整语义，目录权限和链接也属于用户资产；失败时不能留下半成品。
5. **单次 rename 原子 ≠ 整个工作流原子。** 多实体、两个 rename、审核记录、盘点和审计之间仍有失败窗口，需要明确事务状态与恢复策略。[Python os 文档](https://docs.python.org/3.9/library/os.html#os.rename)
6. **建议有效性依赖证据。** 目标内容、被采用的替代品、来源、客户端适配和安检变化应使相关建议过期；无关 Skill 的改变不应强迫全部重新审查。

保留的架构长处：标准库、临时 HOME 测试、固定候选、不自动删除、不以热度评分代替判断、不在脚本里内置模型服务。

## 5. 已确认的问题及优化方向

优先级：P0 为涉及目标越界或资产恢复的缺口；P1 为事实、建议、入口和状态不可信；P2 为效率和持续维护。这里的 P0 不表示已遭外部攻击；威胁前提是用户通过本地工具处理损坏/被改动的归档，或正常操作中发生异常。系统不应被描述为能隔离拥有同一用户权限的恶意程序。

### F01 · P0：恢复校验没有约束 manifest 中的目标路径

证据：`scripts/core/backup.py:151` 的 verify 主要校验 tar 成员；`:235` 将 `original_relative_path` 直接拼到登记根目录。没有统一校验 manifest 内的路径、类型和目录归属。

临时复现：将合法备份的 `original_relative_path` 改为 `../../escaped-fixture`，保持 payload 不变。`verify_backup()` 返回 `ok=True`，`restore_backup()` 返回成功，在登记根目录外写出文件。逃逸目标仍在此次临时 HOME 内。

另外，恢复计划只绑定 backup ID 与路径（`changes.py:166`），没有绑定归档内容摘要。用户确认后同一文件被替换，执行阶段会重新信任新 manifest。

目标：严格解析完整 manifest；路径逐层校验且不穿过链接父目录；计划绑定归档 hash、目标集合与恢复位置，执行前重新核对；损坏对象在任何落地前失败。

### F02 · P0：通过备份自检，仍不一定能往返恢复

证据：`backup.py:267` 重建目录和文件，但没有重建目录内的 symlink，也没有还原目录权限；`:307` 的部分恢复清理顺序会跳过此前已经恢复的实体。

临时复现：

- Skill 内增加 `alias.py -> run.py`：备份自检成功，恢复报树摘要不符，原目录未恢复。
- 增加权限为 0700 的子目录：同样自检成功、恢复失败。
- 两实体备份，将第二个条目的 tree_hash 改成不一致值：verify 仍成功；恢复失败后，第一个实体留在原位置。

目标：备份校验覆盖规范 manifest 与整树摘要；恢复完整类型、链接目标、目录/文件权限；只撤销本事务实际落地的对象；处理链接依赖顺序；验证异常与返回 false 同样需要清理。

### F03 · P0：删除失败回滚、计划状态和审计尚未构成完整事务

证据：`changes.py:421` 仅部分 ChangeError 路径尝试恢复；`:434` 的通用异常只写日志；删除直接 rmtree，更新连续两次 rename；`:352` 先读 inventory 再持锁。`audit.py` 在执行尾部追加结果，尚无持久的执行中状态。

临时复现：

- 删除后的验证函数抛 RuntimeError：目标仍被删除，审计为 `failed: RuntimeError`，没有自动恢复。
- 删除两个实体时第二次删除抛 OSError：只剩一个实体，未恢复原集合。
- 同一个删除计划成功后从备份恢复，再在有效期内重放原计划：再次成功删除。

其他源码缺口：删除理由参数没有进入 plan 的实际摘要；审计的 resulting_hash 写成 backup ID，expected_hash 未填；进程在两次 rename 之间退出的恢复没有测试和日志状态支持。

目标：先备份验证，逐目标在同文件系统做受控移动，记录持久事务阶段；仅清理事务所有的临时实体；失败恢复全部受影响对象；已执行计划不得再次发生物理变更；把文件事务成功与报告刷新失败区分开；可恢复中断，不承诺多个客户端观察到一个全局原子瞬间。

### F04 · P0：计划和执行之间缺少统一的策略与输入验证

证据：`changes.py:79` 的保护主要在创建计划时；`:303` 执行前校验只检查路径字符串和树哈希，没有重新检查 mutable、所属根目录和最新来源保护。`_load_vet()` 只核对 candidate_hash，未校验 verdict 枚举。

临时复现：普通 Skill 生成计划后登记为 builtin-app，apply 仍删除成功。把 `.vet.json` 的 verdict 改成 `typo`，保留正确 hash，候选仍安装成功。

目标：以 data_dir 内权威配置为依据，plan 和 apply 共用同一策略函数；配置损坏应拒绝相关写操作并解释原因；候选必须明确 safe，或 warning 且有第二次真布尔确认；未知值一律拒绝。自建保护与客户端托管保护分别定义，不能把“不进入价值审查”当成内容安全证明。

### F05 · P1：盘点的“已知”“未知”和“失败”混在一起

证据与复现：

- `scan.py:84` 把嵌套 metadata 变为字符串，`:267` 却递归读取 dict。常见 `metadata.requires.bins` fixture 检出依赖数为零，缺命令检查失效。
- `scan.py:491` 目录读失败直接 continue，`fingerprint.py` 的 os.walk 未提供 onerror；部分读不到可能被当作成功扫描。另一部分文件读取错误会直接打断全扫描，表现不一致。
- `scan.py:176`、`provenance.py:47` 丢弃配置损坏 issues；`operational_ok` 默认 true；`scan --json` 的 need_vet 固定为空列表。
- 缺少 inventory 时运行 `check_updates --json`，实际得到 `operational_ok=false`，进程退出码却为 0。
- 工作区统一混入全局统计，`.agents` 与 `.codex` 工作区分配不充分；插件按 `(location_id, plugin_name)` 选最高版本，缺少 marketplace 维度；这属于模型约束不足，当前商业客户端真实启用情况未重新实测。
- Accio 安装回执读取函数已存在，但生产调用链没有接入；同理，文档承诺的 groups.json 分组在当前扫描/报告实现中没有消费者。

目标：结果包含完整性、观察范围、缺失证据及错误；unknown 不按零处理；逐客户端声明规则来源/适用范围；工作区分开建上下文；权威回执不具备时明确显示推断，不把“缓存最大版本”说成已观测加载事实。

### F06 · P1：审查记录的有效性模型不完整

证据：`scan.py:456` 用内容哈希生成 logical_id；`report.py:150` 只按当前 logical_id 找记录，因此真实内容变更后旧记录不再可见。`reviews.py:94` 只比较目标树哈希，未使用替代品/来源等依赖判断。`record_review()` 自动取队列 hash，未要求提交者证明读的是同一对象；safety 不校验枚举。

临时复现：目标脚本变更后，队列显示 needs-recheck，报告却只有一个“未审查”，过期记录数为零；提交错误 skill_tree_hash 和非法 safety 值仍被接受。

目标：保留当前 ID 的兼容性，增加基于安装实例与内容版本的历史连接；目标或所依赖替代品变化可定位过期原因；报告/队列共用有效性计算；记录必须核对明确的目标 hash 与证据快照。证据结构校验只能约束完整性，不能证明 AI 的自然语言结论正确。

### F07 · P0/P1：候选清理缺少所有权边界，上游树可能不完整

证据：`github.py:133` 忽略递归 trees 响应的 truncated；将 `120000` symlink blob 写成普通文件。官方协议明确区分该类型，并要求 truncated 时逐子树拉取。[GitHub Git trees 文档](https://docs.github.com/en/rest/git/trees?apiVersion=2022-11-28)

临时复现：fake GitHub runner 返回 truncated=true，fetch 仍 ok；Git symlink 落地成普通文件。这是协议 fixture，不是针对真实远端下载的测量。

另有独立的 P0 清理边界：check 会 rmtree 暂存根下所有无引用子目录，没有验证本工具所有权。临时实验只在指定 staging 根下创建一个不相关的 sentinel 目录，传入空 inventory 后该目录也被删除。环境变量可覆盖根路径，必须先增加边界保护，不能只把它当缓存优化。

其他缺口：仓库根目录的 SKILL.md 无法正确定位（空 source_dir 的 fixture 返回 source-dir-empty-or-missing）；不校验候选根 SKILL.md、Git submodule 等不支持类型；只根据版本号判断 local-custom；staging 清理只看两轮 updates 引用，未看未过期计划和正在使用者；失败刷新返回 stale 对象却未同步写回缓存，报告可能继续展示旧的成功状态。

目标：协议不完整即拒绝或补齐，不能降格为完整候选；上游差异、本地定制、来源不明分别表示；垃圾回收持锁且只清理确认属于本工具的候选，保护有效计划引用；网络旧缓存必须显式标陈旧。

### F08 · P1：用户实际操作链路与文档承诺不一致

证据与临时复现：

- `backups_list()` 输出 `backup-<id>.tar.gz`，网页将该文件名作为 backup_id 交给 API，底层再次拼前后缀；真实的备份按钮参数会被 API 拒绝。
- `_handle_apply()` 成功后不刷新 inventory 或 report；JS 只 reload。临时实验里物理目标已删除，保存的 inventory 和报告保持原样。
- 更新 API 存在，但 JS 没有 update 操作分支，也没有完整的候选安检 CLI；warning 二次确认未从网页传给引擎。
- 静态删除命令将 `~/skill-keeper/...` 整体 shell quote，`~` 不会展开；恢复按钮没有静态命令，却显示已复制。
- 自定义 data_dir 的 API context、CLI 备份目录和 rescan 子进程不一致，测试/多环境有误读其他数据的可能。

目标：一个应用服务入口承接 CLI/API；参数与返回结构一致；删除、更新、恢复分别有可执行命令；页面展示可审阅计划后确认；动作后发布新快照；失败刷新必须显示实际状态，不宣称已经回滚。

### F09 · P2：审查队列重复计算，先修算法，再考虑增量缓存

`reviews.py` 对每个第三方都重新生成全库相似对和替代候选；`overlap.py` 每次重读全部 SKILL.md。

固定虚构样本、计数探针实测：

| 逻辑 Skill 数 | 正文读取次数 | 相似度计算次数 | 带计数探针耗时 |
|---:|---:|---:|---:|
| 20 | 800 | 4,180 | 0.049 秒 |
| 40 | 3,200 | 32,760 | 0.297 秒 |
| 80 | 12,800 | 259,120 | 2.299 秒 |

这符合重复构建导致的近三次方增长，不宜通过多线程掩盖。目标是单次构建读取每份正文一次、计算每对一次，并复用索引。数值等价和操作次数上限应成为验收标准；壁钟时间只作辅助，以免机器差异导致假失败。

### F10 · P2：项目自我扫描把运行数据也当成 Skill 内容

`fingerprint.py` 只排除 `.DS_Store`、`__pycache__`、`.pyc`；项目通过共享库符号链接被扫描，其 data、backups、Git 历史均进入完整树。临时实验确认，写一个运行时 inventory 即改变 Skill 哈希。

这不是要全局忽略 data/backups：第三方可能恰好把真正可执行内容放在那里，放宽完整指纹会削弱安检。推荐把本项目配置、运行态、备份移到加载树外，由显式迁移处理；本轮先做可选路径与迁移预演，不自动移动真实数据。Git 元数据与可发布 Skill 内容的边界需要独立、版本化定义。保持普通第三方完整树指纹不变。

### F11 · P1/P2：能力和约束文档仍有漂移，自动防线不够

- `.gitignore` 没有列出文档声称已忽略的 `data/client-locations.json`；该文件可包含个人路径。
- SKILL frontmatter 版本为 2.1.1，项目状态已描述到 2.1.3；源码和 README 仍留有旧 Haha/重复加载文案。
- “恢复 CLI”“网页更新”“分组”出现文档承诺与实际入口不一致。
- 并发保护主要覆盖 apply；审查记录/ignore 等 read-modify-write 仅原子替换，仍可能丢失并发写入。
- 当前无仓库内 CI 配置，测试未覆盖上述失败组合；部分 fixture 的目录布局与后来的适配器修改不同步。`test_tar_link_and_device_members_are_rejected` 生成未压缩 tar，而 verify 固定用 r:gz 打开，因此该测试可以仅因压缩格式不符通过，不能证明真正命中了链接/设备拒绝分支。

目标：已承诺但断开的主要工作流补通；明确区分原始设计、当前能力、历史运维记事和候选改进；增加固定虚构验收夹具和故障矩阵；新增个人数据路径必须配忽略检查。文档同步附着在每个功能任务，不另做无限范围的“整洁重构”。

## 6. 建议的优化路径与取舍

| 方案 | 能解决什么 | 代价与不足 | 判断 |
|---|---|---|---|
| 继续逐个打补丁 | 快速消除眼前 bug | 相同策略仍多处维护，异常组合容易漏 | 只适合紧急止血 |
| 分阶段集中核心规则 | 统一目标策略、恢复合同、观察状态、审查有效性和操作入口 | 需要有兼容性与失败注入测试 | **推荐** |
| 整体重写/数据库化/前后端框架化 | 表面上有更整齐的技术栈 | 迁移成本高，现有资产与安全知识容易丢失，不能自动消除上述语义问题 | 本轮不做 |

推荐发布顺序：

1. **安全修复阶段**：F01–F04 加 F07 的清理边界，包含严格备份、完整往返、事务状态、执行时策略和暂存所有权保护。此阶段独立验收。
2. **可信工作流阶段**：F05–F08 与 F11 的入口/隐私部分；用户和 Agent 看到同一套事实与状态。
3. **效率阶段**：F09、F10 与持续检查；先用计数证明优化，再决定是否需要持久增量索引。

不纳入本轮：更多客户端、卸载残留全盘搜索、主题换肤、市场下载量、使用遥测、自动清理、联网模型服务、常驻守护进程、跨设备同步、Windows 移植、数据库迁移。它们可在核心验收通过后按具体需求选择。

## 7. 新一轮验收必须守住的结果

- 恶意/损坏 manifest、候选、配置只能明确失败；没有目录外写入，没有把未知状态显示成已检查。
- 删除/更新/恢复的正常异常、验证异常和进程中断分别有证据；恢复后的内容、路径、权限、链接和受影响实体集合符合计划。
- 同一计划重放不发生第二次物理变更；状态回执和审计能够区分提交成功、恢复成功、需要恢复、报告过期。
- 目标或已采用替代品变化可解释地使审查过期；无关变化不会让全部审查失效。
- CLI、服务 API 和报告的同一动作使用同样的目标、数据目录和新快照。
- 现有 126 项回归语义不退化；不通过删测试、skip、放宽断言、假成功或 mock 掉被测对象达标；新测试使用虚构临时 HOME。
